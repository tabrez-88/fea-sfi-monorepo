## Auth subsystem — gaps #1–#3, #15–#22

### Architecture

`apps/sfi-api/src/modules/auth/` is a self-contained NestJS module registered in `app.module.ts`. Global `JwtAuthGuard` (via `APP_GUARD`) protects every route by default; routes opt out with `@Public()`. User identity is available on any authenticated handler via `@CurrentUser()`.

### Schema additions

Three new models in `prisma/schema.prisma`:

- **`User`** — `id` (cuid), `email` (unique), `passwordHash`, `name`, `avatarUrl?`, `role: UserRole` (ADMIN / USER), `lastLoginAt?`, timestamps.
- **`RefreshToken`** — `id` = JWT `jti` (cuid), `userId` FK, `tokenHash` (SHA-256 of the raw token), `expiresAt`, `revokedAt?`, `replacedBy?` (chain pointer for reuse detection).
- **`PasswordResetToken`** — `id`, `userId` FK, `tokenHash` (SHA-256), `expiresAt`, `usedAt?`.

### Services

| Service | Responsibility |
|---|---|
| `PasswordService` | bcrypt hash + compare at cost 12 |
| `TokenService` | JWT sign/verify, refresh rotation, reuse-detection revocation, password reset helpers |
| `EmailService` | nodemailer transporter; dark-header FEA branding; falls back to console log when SMTP creds absent |
| `AuthService` | register (conflict check → hash → issue tokens), login (timing-safe dummy hash on unknown user), refresh, logout, forgotPassword (idempotent invalidation), resetPassword ($transaction), me |

**Refresh token strategy:** each refresh issues a new token and marks the old one `replacedBy` the new ID. If a used (replaced) token arrives again, the entire chain is revoked (`updateMany` where `id IN [chain]`) — this kills a session if a stolen token is detected. `jti` = `RefreshToken.id` so revocation is an O(1) DB lookup.

### Endpoints

```
POST /auth/register        — @Public()
POST /auth/login           — @Public()
POST /auth/refresh         — @Public()
POST /auth/logout          — @Public() (invalidates refresh token on server)
POST /auth/forgot-password — @Public()
POST /auth/reset-password  — @Public()
GET  /auth/me              — authenticated; returns AuthUserDto
```

All endpoints return consistent `{ user, tokens }` shape on success (except logout/forgot-password which return `{ message }` / `{ message, email }`).

### Config wiring

- **JWT secrets** — `JWT_ACCESS_SECRET` + `JWT_REFRESH_SECRET` in `.env`; also loaded from GCP Secret Manager (`SECRET_KEYS` array updated in `gcp-secrets.service.ts`). Access token: 15 min, refresh token: 7 d.

## FEA-1 — Login, FEA-2 — Register, FEA-3 — Forgot Password

The three auth screens had placeholder API calls since April 8. With the auth subsystem live, all three are now wired to real endpoints.

### FEA-1 Login

**`src/app/(auth)/login/page.tsx`**

`useLogin()` mutation hits `POST /auth/login`. On success:

1. Stores access token in memory (Zustand `useAuthStore`).
2. Stores refresh token in `httpOnly` cookie via a lightweight `POST /api/auth/set-cookie` Next.js route handler.
3. Populates `useAuthStore.user` from `response.user` — this immediately hydrates the navbar without waiting for a `/me` round-trip.
4. Redirects to `/dashboard`.

On 401: inline "Invalid email or password" under the submit button (no field-level error to avoid email enumeration).

### FEA-2 Register

**`src/app/(auth)/register/page.tsx`**

`useRegister()` mutation hits `POST /auth/register`. Fields: Full Name, Email, Password (min 8 chars, must include at least one number), Confirm Password (Zod `.refine` cross-field match). On success: same token storage flow as login, redirect to `/dashboard`.

On 409 conflict: inline "An account with this email already exists."

### FEA-3 Forgot Password

**`src/app/(auth)/forgot-password/page.tsx`**

Two-state UI:

- **Input state:** email field + "Send reset link" button. `useForgotPassword()` hits `POST /auth/forgot-password`.
- **Success state:** transitions after successful mutation. Displays the email address from `ForgotPasswordResponseDto.email` — e.g. "We sent a reset link to **user@example.com**." Back-to-login link at the bottom.

Error state (non-existent email) intentionally renders the same success state — API returns `{ message, email }` regardless to prevent email enumeration.

### Navbar hydration

**`src/app/(dashboard)/layout.tsx`**

On mount, `GET /auth/me` is called via `useCurrentUser()` if `useAuthStore.user` is null (e.g. on hard reload after access token expires). Response populates `name` and `avatarUrl` in the store. Navbar renders the user's name next to a fallback avatar (initials from name when `avatarUrl` is null — Cloud bucket for real avatars is deferred to a later sprint).

Token refresh is handled by an Axios request interceptor: on 401, attempts `POST /auth/refresh` using the refresh token cookie, retries the original request once with the new access token.
