## Infra — sfi-admin Cloud Run Setup Plan

Reuses every piece of the existing sfi-api GCP footprint: the `fea-development-486410` project, the `sfi-fea-cloudrun` service account, the `github-pool` Workload Identity Federation binding, and the `sfi-fea-images` Artifact Registry repo. Only sfi-admin-specific plumbing is new.

### 1. Dockerfile — `apps/sfi-admin/Dockerfile` (new)

Multi-stage, Next.js standalone output for a slim runtime image:

- Base: `node:20-alpine`
- Enable pnpm via corepack, `pnpm install --frozen-lockfile` with workspace filtering
- `pnpm --filter @sfi-fea/sfi-admin build` with `NEXT_PUBLIC_*` build-args (see §3 — this is the main gotcha vs NestJS)
- Runtime: copy `.next/standalone` + `.next/static` + `public`, run `node server.js` on `${PORT:-3000}`

Set `output: 'standalone'` in `apps/sfi-admin/next.config.ts` so the build produces the minimal self-contained server.

### 2. Secret Manager

Only two secrets — the admin portal is a thin client over sfi-api, no direct DB access:

| Secret | Value | Notes |
|---|---|---|
| `NEXT_PUBLIC_API_URL_STAGING` | sfi-api-staging Cloud Run URL | Must be set **before** the first admin build — NEXT_PUBLIC inlined at compile time |
| `NEXT_PUBLIC_APP_ENV_STAGING` | `staging` | Drives the zod enum in `src/lib/env.ts` |

```bash
echo -n "https://sfi-api-staging-xxxxxx-et.a.run.app" \
  | gcloud secrets create NEXT_PUBLIC_API_URL_STAGING --data-file=-
echo -n "staging" \
  | gcloud secrets create NEXT_PUBLIC_APP_ENV_STAGING --data-file=-
```

### 3. Build-time vs runtime env — the NEXT_PUBLIC gotcha

sfi-api (NestJS) reads env vars at **runtime**, so Cloud Run's `--set-secrets` flag is enough. sfi-admin (Next.js) inlines `NEXT_PUBLIC_*` vars at **build time**, so the values must be present when `next build` runs inside the Docker image.

CI approach:
1. Pull both secrets in the GitHub Actions job via `google-github-actions/get-secretmanager-secrets@v2`
2. Pass them as `--build-arg` to `docker build`
3. Dockerfile re-exports them as `ENV` before `pnpm build` so Next.js picks them up
4. Also pass them via `--set-secrets` on `gcloud run deploy` so server-side code (if any is added later) sees them at runtime too

This is the single most important deviation from the sfi-api deploy pattern.

### 4. CI — extend `.github/workflows/deploy-staging.yml`

Add a `deploy-sfi-admin` job mirroring the existing `deploy-sfi-api` job:

- Authenticate via `google-github-actions/auth@v2` with the existing `GCP_WORKLOAD_IDENTITY_PROVIDER` + `GCP_SERVICE_ACCOUNT` secrets (no new GitHub secrets needed)
- Resolve `NEXT_PUBLIC_API_URL_STAGING` + `NEXT_PUBLIC_APP_ENV_STAGING` from Secret Manager
- `docker build -f apps/sfi-admin/Dockerfile --build-arg NEXT_PUBLIC_API_URL=$url --build-arg NEXT_PUBLIC_APP_ENV=$env -t asia-southeast2-docker.pkg.dev/fea-development-486410/sfi-fea-images/sfi-admin-staging:$GITHUB_SHA .`
- Push + `gcloud run deploy sfi-admin-staging --port=3000 --allow-unauthenticated`

### 5. CORS on sfi-api

Once the admin Cloud Run URL is known (first deploy), add it to the existing `CORS_ORIGIN_STAGING` secret and redeploy sfi-api so it picks up the new version:

```bash
echo -n "https://sfi-admin-staging-xxxxxx-et.a.run.app,http://localhost:3000,http://localhost:3002" \
  | gcloud secrets versions add CORS_ORIGIN_STAGING --data-file=-

gcloud run services update sfi-api-staging --region=asia-southeast2
```

4. Open a deal → Deal Overview fetches real data, DealSidebar renders alongside icon-rail
