## BE — Role Taxonomy Option B (FB-002)

Implemented the architecture decision confirmed on April 14. The `ParticipantRole` enum is gone; participant payment behavior is now driven by `ParticipantBehavior`.

### Schema migration

```prisma
// Removed:
enum ParticipantRole {
  DISTRIBUTOR
  PRODUCER
  SALES_AGENT
  INVESTOR
  TALENT
  OTHER
}

// Added:
enum ParticipantBehavior {
  DISTRIBUTION_FEE   // takes a % off gross before any splits
  RECOUPMENT         // recoups a fixed amount before profit splits
  NET_PROFIT_SHARE   // receives a % of net profit
  FLAT_FEE           // fixed payment regardless of revenue
  PASS_THROUGH       // no payment — tracking only
}

model Participant {
  // Removed:
  // role  ParticipantRole

  // Added:
  roleName     String              @map("role_name")
  behaviorType ParticipantBehavior @map("behavior_type")
}
```

Migration applied with a clean name (first formal migration in this project):
```bash
npx prisma migrate dev --name replace_participant_role_with_behavior_type
```

### Settlement engine — behavior branching

The engine previously used `role` as a hint for payment type. It now switches directly on `behaviorType`, which is explicit and asset-class-agnostic:

```typescript
function calculateAllocation(
  participant: ParticipantWithBehavior,
  grossRevenue: number,
  netAfterPrior: number,
): AllocationResult {
  switch (participant.behaviorType) {
    case 'DISTRIBUTION_FEE':
      return { amount: grossRevenue * participant.percentage, deductsFromGross: true };
    case 'RECOUPMENT':
      return { amount: Math.min(participant.fixedAmount, netAfterPrior), deductsFromNet: true };
    case 'NET_PROFIT_SHARE':
      return { amount: netAfterPrior * participant.percentage, deductsFromNet: false };
    case 'FLAT_FEE':
      return { amount: participant.fixedAmount, deductsFromNet: false };
    case 'PASS_THROUGH':
      return { amount: 0, tracking: true };
  }
}
```

This replaces the previous role-to-behavior mapping table that was leaking film-industry assumptions into the engine.

## Sprint 2 Opener — sfi-admin GCP Setup (next)

With Sprint 1 done, the next infra step is deploying `apps/sfi-admin` to a staging Cloud Run service alongside the existing `sfi-api`. The GCP project, service account, Workload Identity Federation, and Artifact Registry from [`docs/infrastructure/GCP_SETUP_GUIDE.md`](../infrastructure/GCP_SETUP_GUIDE.md) are already live for `sfi-api-staging` — we reuse all of those. Only the sfi-admin-specific pieces need doing.

### Checklist for `sfi-admin-staging`

**1. Dockerfile** — new file `apps/sfi-admin/Dockerfile`:
- multi-stage: `node:20-alpine` base, `pnpm install --frozen-lockfile`, `pnpm --filter @sfi-fea/sfi-admin build`, `next start -p ${PORT:-3000}`
- standalone output (`next.config.ts` → `output: 'standalone'`) to keep the runtime image lean

**2. Secrets (Secret Manager)** — only two, since the admin portal is a thin client over `sfi-api`:

| Secret | Value | Notes |
|---|---|---|
| `NEXT_PUBLIC_API_URL_STAGING` | `https://sfi-api-staging-xxxxxx-et.a.run.app` | Pulled from the existing `sfi-api-staging` Cloud Run URL after promotion |
| `NEXT_PUBLIC_APP_ENV_STAGING` | `staging` | Drives the `env.ts` zod enum |

Create commands follow the same `echo -n | gcloud secrets create ..._STAGING --data-file=-` pattern in §6 of the GCP guide.

**3. GitHub Actions** — extend the existing deploy workflow with a `deploy-sfi-admin` job:
- reuses `GCP_WORKLOAD_IDENTITY_PROVIDER` + `GCP_SERVICE_ACCOUNT` (no new GitHub secrets)
- pushes image to `asia-southeast2-docker.pkg.dev/fea-development-486410/sfi-fea-images/sfi-admin-staging`
- `gcloud run deploy sfi-admin-staging --port=3000 --allow-unauthenticated --set-env-vars="NODE_ENV=production" --set-secrets="NEXT_PUBLIC_API_URL=NEXT_PUBLIC_API_URL_STAGING:latest,NEXT_PUBLIC_APP_ENV=NEXT_PUBLIC_APP_ENV_STAGING:latest"`

Important: `NEXT_PUBLIC_*` vars must be available **at build time** for Next.js to inline them — the Docker build step needs `--build-arg NEXT_PUBLIC_API_URL=...` wired in, not just runtime env vars. This is the gotcha vs sfi-api's NestJS runtime-only env.

**4. CORS update on sfi-api** — once the admin Cloud Run URL is known, add it to `CORS_ORIGIN_STAGING`:

```bash
echo -n "https://sfi-admin-staging-xxxxxx-et.a.run.app,http://localhost:3000,http://localhost:3002" \
  | gcloud secrets versions add CORS_ORIGIN_STAGING --data-file=-
```

Then `gcloud run services update sfi-api-staging` to pick up the new secret version.

**5. Smoke test plan** — after first deploy:
- Hit `/` on `sfi-admin-staging` → expect redirect to `/login`
- Log in with a seeded staging user → land on `/dashboard`
- Navigate to `/deals`, open a seeded deal → verify Deal Overview loads real data
- Toggle sidebar, open+close mobile drawer on a phone viewport → confirm animations
